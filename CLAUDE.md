## 0. TL;DR

Branded **“Signal to Signature”** (v4.0) — a single‑file web app + a local full‑wave simulation bridge that evaluates **lightweight, thin‑film‑coated materials (flagship: MXene‑coated basswood) as replacements for heavy solid‑metal satellite waveguides and horn antennas.** It predicts a material's RF loss, weight and launch‑to‑orbit cost instantly (analytical engine), and validates the chosen design with a real 3‑D FDTD solve (openEMS). Current version: **v4.0**.

Development happens on the **Mac** (Homebrew openEMS); a Windows PC runs the always-on bridge for a
remote tester. **Sync is via git** (a private repo), not file-copy tools — file sync can't merge and

machine-local installs are git-ignored (see `.gitignore`); the Windows runtime (`C:\opt\openEMS` incl.

**outside the repo** and is set up once per machine — see `openEMS/WINDOWS_SETUP.md`.

**Windows-portable, macOS-unchanged code (do NOT strip it):** the openEMS Python renderers
(`render_field.py`, `render_field_freq.py`, `render_rcs.py`, `cad/render_horn.py`, `cad/view_stl.py`)
contain blocks guarded by `if os.name == "nt":` — a **Mesa software-OpenGL preload** (so off-screen

macOS `add_volume` path (`OPENEMS_FIELD_RENDER=volume|surface`, default surface on Windows only). These
are **no-ops on macOS/Linux** — the Mac render path is byte-for-byte unchanged. When editing these files
for a feature, keep the Windows blocks intact.

## 2. What it is (research context)

Solid copper/aluminum waveguides and horns are electrically excellent but heavy, and every kg to orbit costs thousands of dollars. The research question: can a **lightweight structure with a thin conductive coating** (flagship MXene = Ti₃C₂Tₓ on basswood) do the same job at a fraction of the mass? The tool quantifies the RF‑performance ↔ weight ↔ cost trade for any material, across the **X (8–12 GHz, WR‑90), Ku (12–18 GHz, WR‑62), K (18–27 GHz, WR‑42)** satellite bands.

## 3. Architecture — two engines

**Engine 1 — Analytical (in‑browser, instant).** Closed‑form microwave physics in vanilla JS inside `waveguide_simulator.html`. Rectangular‑waveguide TE10 conductor attenuation, skin‑depth + finite‑coating corrected, complex ε/μ, a multilayer transfer‑matrix stack, far‑field/horn equations, Monte‑Carlo UQ. Recomputes on every control change. Validated against 13 textbook anchors.

**Engine 2 — openEMS full‑wave FDTD (local).** A Python **Flask bridge** (`openEMS/openems_server.py`, port **8731**) serves the HTML and, on "Run" requests, launches **GNU Octave** scripts that drive **openEMS** (free FDTD Maxwell solver), post‑processes the field dumps with **Python/NumPy/PyVista**, and streams charts/images/3‑D field data back to the page. The page must be opened at `http://localhost:8731` for the Run buttons to work (same‑origin fetches to `/run`, `/run_horn`).

Everywhere the two overlap, the **analytical curve is dashed** and the **openEMS curve is solid**, so agreement is visible.

## 4. Run & verify

**Analytical only (no server):** open `waveguide_simulator.html` in a browser. Everything works except the "Run on openEMS" buttons.

**Full‑wave (the bridge):**
```
pip install flask pyvista imageio imageio-ffmpeg numpy   # (use --break-system-packages if needed)
# install openEMS + GNU Octave (see openEMS/SETUP.md)
python "openEMS/openems_server.py"        # prints http://localhost:8731
```

## 8. Gotchas / landmines (learned the hard way)

- **`var()` does NOT resolve inside SVG presentation attributes** (`fill="var(--x)"`, `stroke="var(--x)"`). Use literal hex or `style="fill:var(--x)"`. (Rendered the hero art black once.)
- **A raw `<` in MathJax equations** is parsed as an HTML tag and can eat `</div>` and blank whole tabs. Use `\lt` (and be careful with `|S11| < -10` etc.).
- **Global Chart.js plugins that throw blank ALL charts.** Keep chart customizations per‑chart and defensive.
- **Chart.js created inside a `display:none` container inits at 0×0 and never repaints when shown** (the canvas has no container width at construction). Symptom: a blank/short chart panel while the headline + any raw‑`<canvas>` heatmap render fine. **Always reveal the panel (`fig.style.display=''`) BEFORE `new Chart(...)`, then call `chart.resize()` (synchronous).** This bit the RL tab's RL‑vs‑freq + RCS charts and the Inverse‑RAM Pareto/refl charts (all fixed: draw functions now show‑then‑create, and `repaintRL()` resizes). NB: the in‑app automation Browser pane has a **0‑width viewport** (full‑width panels collapse; only CSS‑grid `minmax(300px)` tracks get sized), so you cannot confirm full‑width Chart sizing there — force a width on the panel and call `resize()` to verify the chart paints, or check in a real browser.
- **Down‑range profile (RCS `range` sim): reference the IFFT to the dominant scatterer, not absolute range 0, and floor non‑finite dB.** openEMS NF2FF far‑fields carry the reference‑sphere phase `e^{-jkR}`, a large linear‑in‑f term that displaces the whole down‑range profile by the (arbitrary) far‑field distance — often **hundreds of mm**, outside the plotted ±clip window. `drawRange` normalized the small window to the **global** peak (which sat outside it), pushing every plotted point to ≈−48 dB, **below the chart's −40 dB y‑floor → axes drew but no curve** (the exact symptom the owner reported). Fix: track the peak bin `npk`, reference ranges to it (`d=n−npk` wrapped to ±M/2), normalize to that peak (dominant scatterer = 0 mm / 0 dB — standard ISAR practice), and floor non‑finite dB (`20·log10(0)=−∞`, and `(−Infinity).toFixed()` → the string `"-Infinity"` → `+…` = NaN, which Chart.js silently drops). Any IFFT / peak‑normalized chart with a **fixed** y‑axis needs both guards. Validated: dominant return at 0 dB/0 mm, 88 visible points (was 0).
- **Monostatic PO plate sinc uses the FULL dimension: `u = k·w·sinθ`** (not `k·(w/2)`). Backscatter is round‑trip, so the aperture phase slope is `2k sinθ` over ±w/2 → argument `k·w·sinθ` (Knott `sin(ka·sinθ)/(ka·sinθ)`, a = full dim; first null at `sinθ=λ/2w`). A half‑argument bug put every plate null/sidelobe at 2× the correct angle (boresight `4πA²/λ²` is unaffected — the error hides at θ=0). ## 13. v4.0 — the shape-validity gate, rotating exports, and construction-aware materials

**⚠ Geometric validity gate on the shape optimiser (the owner applied an improved shape and asked "is this shape actually even viable lol").** It was not: the lever grids reached far enough to fold the surface and squash parts, and nothing checked. Every candidate is now **audited before it is allowed to score** — `meshAudit(vm,tris,axisHint,sideHint)` + `validateShape(ref,vm2,tris,maxVolLossPct)`, wired into `stepInner()` ahead of `evalShape`. Rejection criteria: >0.5 % inverted normals (the skin has passed through itself), >2 % of facets collapsed below a fifth of their reference area (a sliver's normal is meaningless, so the physics stops being trustworthy — the same reasoning as the `minFacetQuality` guard in `buildEdges`), enclosed-volume loss past a user budget (`#cad-opt-vol`, default 15 %), inflation past 1.5×, wetted area outside [0.6, 1.8]×, any part flattened below 35 % of a reference dimension, or an appendage driven into the body. All eight lever grids were retuned to drop the extremes. `REF=meshAudit(vm0,tris)` is computed once and every candidate is measured against it, so **the volume budget is cumulative across stages** (measured against the user's original model, not the previous stage) — the caveat text says so, because a change that passes alone can be refused once an earlier one is in the chain.

⚠ **Two false positives found by live testing, both material.** The penetration test originally asked "is this part's vertex inside the body's axis-aligned bounding box?". That is **rotation-sensitive**: rolling a fin about the body axis preserves its true clearance exactly but sweeps its vertices through the box's CORNERS, so the gate reported "drives a part into the body" for a rotation that penetrates nothing — and *canting the appendages* is one of the most effective, most buildable signature fixes there is. It now measures **radial distance about the body axis** (axis = the body's longest bbox dimension; inscribed transverse radius, which under-covers a square section's corners, i.e. errs toward NOT flagging). Second: a **nose cone or nozzle is in series with the body**, not attached alongside it, so pulling its profile inward — exactly what sharpening a nose does — is not penetration; only parts whose axial span overlaps the body's by ≥50 % of their own extent are tested (`alongside`, decided on the reference and reused so a deformation cannot change the population being tested). Measured effect on the rocket demo, nose-on ±60°: rejections **29 → 19 → 12**, scored candidates **31 → 41**, and the result went from **−2.7 dB to −10.0 dB** because the physically-correct fix was being thrown away. Both fixes are locked by reusing `ref.ax`/`ref.alongside`.

**⚠ The rotating GIF/HTML did not rotate the object at all (owner: "the gif is whack").** `captureTurn` called `viewerDraw(angle)`, which only **recolours facets** for a radar at that aspect, and then pinned `V.grp.rotation` to the user's fixed view on every frame — so the export was a static silhouette with shifting colours. Three distinct faults, each caught by measuring the frames rather than looking at them:

1. **No rotation.** The spin is now applied to the group as well as the colours, through the **quaternion** (`tilt · spin · align`), not `rotation.x/y` — Euler order would otherwise make the result depend on how the user had dragged the view.
2. **Clipped.** The first fix spun about the sweep-plane normal (model z for an azimuth sweep), which stands a 980 mm rocket on its tail: silhouette height measured 194 px on *every* frame, i.e. exactly the canvas height, top and bottom cut off. It now finds the mesh's **longest bbox axis and lays it horizontal**, spinning about screen-vertical — the ordinary product turntable — with `V.dist × 1.18` for margin.
3. **Invisible for half the turn.** Facets facing away are painted `[0.09,0.10,0.13]`, essentially the `#0d1117` background. That is right for the interactive viewer (the slider is parked at one aspect and hiding the far side reads as depth) and wrong for a turntable: at 180° only a 30 px sliver rose above the background. `viewerDraw` took an optional third `awayRGB` argument; the turntable passes a visible slate `[0.27,0.30,0.34]`.

Colours are computed **once**, at the peak look angle, and turn with the object — recolouring per frame while the object also turns would imply a correspondence between screen orientation and aspect angle that does not hold for an arbitrary uploaded mesh and either sweep plane. The captions say so.

**Two more faults the owner's screenshot exposed after that.** ④ **The export inherited the live canvas's aspect ratio**, so the same model framed differently on every machine — my test panel was 1200×880 (1.36) and fitted; the owner's was wider and shorter (~1.86) and cut the model off at the edges. `captureTurn` now renders at a **fixed 480×360** by temporarily resizing the renderer, so the output is identical everywhere and is the shape the fit calculation is solved for. ⑤ `V.base=2.2` is **closer than a unit sphere fits**: at the camera's 45° vertical FOV the distance that just contains radius 1 is `1/sin(22.5°) = 2.613`, so the 1.18× margin I first guessed (2.596) was still inside it. It is now computed — `1/sin(atan(min(tanV, aspect·tanV))) × 1.06` — exact for any aspect and any model, since `viewerDraw` normalises to a unit bounding sphere. Tilt went 0.28 → 0.45 rad so it reads as a 3/4 view rather than a flat bar.

⚠ **`renderer.setSize()` takes CSS pixels and multiplies by the device pixel ratio; `canvas.width/height` are DEVICE pixels.** Restoring the viewer from `cv.width` doubled it (1200×880 → 2400×1760) on a 2× display. Save and restore with `renderer.getSize(vec)`.

**How to verify this (screenshots do not work here).** The in-app Browser pane reports `visibilityState=hidden`, so injected DOM never paints and screenshots come back blank — measure the frames instead. Extract the 24 embedded JPEGs from `model_3D_rotating.html`, draw each to a canvas, and threshold against the background to get a per-frame silhouette. Final state on the rocket demo at 480×360: silhouette 92×96 → 333×185, worst margin over all 24 frames 52 px, every frame ≥6725 object px, and the live viewer restored to exactly its original size. **0° and 180° matching is the load-bearing check** — a four-fin rocket must be symmetric under a half turn, and it was 87 vs 30 while fault 3 was live, which is what exposed it.
